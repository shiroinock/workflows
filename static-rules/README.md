# 共通の静的ルール

Claude のレビューで繰り返し出た指摘のうち、静的解析で安く早く見つけられるものをルールにして置く場所。ルールは [ast-grep](https://ast-grep.github.io/) で書き、`.github/workflows/rule-harvest.yml` が週に1度、レビューの指摘からルールの候補を集める(issue「ルール候補」)。

## ルールの置き場所を決める順番

指摘を静的解析に回すときは、上から順に当てはまるところに置く。ast-grep は、ほかのどのツールでも書けない穴を埋めるためだけに使う。

1. **そのリポジトリがすでに回しているツールに、同じルールが組み込みである** → そのルールを有効にする。構文解析が1回増えることもなく、保守はツール側がし、自動修正も付いていることが多い。`ts-template` と、該当するリポジトリの `biome.json`・Ruff の設定などを変える PR を出す。
2. **型の情報・ファイルをまたぐ解析・フレームワークの意味が要る**(React の hooks の依存配列、Promise の投げっぱなし、a11y など) → 型を扱えるツールに任せる。ast-grep は構文の木しか見ないので書けない。Biome で書けないものが溜まったら、oxlint などを `STANDARDS.md` に足すかを別に決める。
3. **構文の形だけで判定でき、どのツールにも無い** →
   - JS/TS だけに効けばよく、そのリポジトリが Biome を回しているなら、Biome の GritQL プラグインも考える(解析が1回で済む。ただしリポジトリごとに配ることになり、自動修正ができるかは版による)。
   - Python・Rust・シェルなど、手軽に独自のルールを足す仕組みが無いもの、または複数の言語・リポジトリに同じルールを効かせたいものは、ここに ast-grep で書く。

ツールの版上げで同じルールが組み込みになったら、ここのルールは消してそちらを有効にする(週1回の収集が、その候補も出す)。

## ルールの書き方

- `rules/<id>.yml` に1つのルールを書く。`id` はファイル名と同じ、英小文字とハイフン。`message` は日本語で、何がなぜ良くないかを1文で書く。`note` に直し方を書く。
- 機械的に直せるものは `fix:` を付ける。意味が変わりうる直しは付けない。
- `severity` は `error` にする(CI を落とすもの)。気づかせるだけなら、ルールにしない。
- `tests/<id>-test.yml` に、引っかかる例(`invalid`)と引っかからない例(`valid`)を書く。元になったレビューの指摘のコードを手がかりにするが、非公開のリポジトリのコードはそのまま写さず、同じ形の例を新しく書く。
- ルールを足す・変える PR では、`rules-impact` の検査が全リポジトリの既定ブランチに当てた件数を出す。元の指摘と関係のない場所で多く引っかかるなら、誤検知を疑って絞る。

## 使い方

```bash
nix run github:shiroinock/workflows#rules              # 検査する
nix run github:shiroinock/workflows#rules -- --fix     # 直せるものを直す
```

リポジトリで外したいルールは、`.github/static-rules-off` に1行に1つ `id` を書く(`#` から後ろはコメント)。CI と手元のどちらでも効く。
